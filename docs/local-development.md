# Local development and project access

Use Node 24, npm and Docker Desktop with Linux containers. This environment contains synthetic project data only. IntelliGrid's web server uses the public Supabase key and the signed-in user's session; it never uses the service-role key.

## First start (PowerShell)

```powershell
npm ci
docker desktop start
docker network create --driver bridge --opt com.docker.network.bridge.host_binding_ipv4=127.0.0.1 intelligrid-local
npx supabase start --network-id intelligrid-local -x realtime,imgproxy,mailpit,postgres-meta,studio,edge-runtime,logflare,vector,supavisor
New-Item -ItemType Directory -Force .cache | Out-Null
npx supabase status -o env > .cache/supabase.env
npm run local:bind
npm run seed:local
npm run dev
```

If the network already exists, reuse it. `local:bind` restricts the database and gateway ports to `127.0.0.1`; the CLI currently publishes explicit wildcard addresses even on a network configured for loopback. It preserves volumes and the gateway configuration, verifies container health, and restores the original container if replacement fails. It touches only `supabase_db_intelligrid` and `supabase_kong_intelligrid`. Re-run it after any CLI operation that recreates these containers. Do not expose Docker's control socket over TCP.

The web app is at `http://localhost:3000`. Open `/login`. `APP_ORIGIN` must match the browser origin exactly; `localhost` and `127.0.0.1` are different origins. Use the localhost URL for form submissions. API port: 56321; PostgreSQL port: 56322. No hosted Supabase account is needed for this phase.

`seed:local` writes `apps/web/.env.local` with the URL, public key and application origin. Operator credentials stay in ignored `.cache/supabase.env`. Random local account passwords are in ignored `.cache/demo-accounts.json`; open that file locally to sign in. Never paste or commit either file. There is no public signup or browser role switch.

## Rebuild the synthetic database

This removes this project's local database contents. Use it only for the disposable IntelliGrid development stack, never a shared or hosted database.

```powershell
npm run db:reset:local
npx supabase status -o env > .cache/supabase.env
npm run local:bind
npm run seed:local
npm run test:seed
npm run test:database
```

Both startup and reset must use `--network-id intelligrid-local`. A reset without it can recreate the database on another network while Auth/Storage remain on the first. The supplied reset script includes the network ID. The seed preserves existing assignments and immutable history on repeat runs. If Auth accounts exist but their local credential file is missing, it refuses to silently reset their passwords.

## Audited membership changes

Project creation and membership provisioning are operator commands, not public web endpoints in this phase. `provision_project` and `set_project_member` are executable only by `service_role`. The web app never imports that credential. The local seed uses both commands. Membership changes lock the project, check the expected version, increment its policy version and record the before/after values in `admin_audit`. Assignment changes use the same project lock, then re-check the actor's current membership.

For an operator change, create an ignored `.cache/member-change.json`, then run `npm run admin:member -- .cache/member-change.json`. Required fields:

```json
{
  "p_project": "project UUID",
  "p_user": "real Auth user UUID",
  "p_expected_version": 1,
  "p_member": {
    "display_name": "Synthetic user name",
    "role": "reporter",
    "contractor_id": "contractor UUID",
    "discipline_scope": ["Civil"],
    "work_front_scope": ["Pump bay / P-101"],
    "capabilities": [],
    "active": false
  },
  "p_actor": "local operator name",
  "p_reason": "Membership revoked after transfer"
}
```

Use the current membership version from the database. An empty work-front array means all locations within the allowed contractor and disciplines. Capabilities are reserved data in Phase 2; they grant no extra permissions. Roles and scopes enforce all current actions. Phase 3 review is restricted to current planner/manager members; supervisor verification is Phase 4. Broadening a member's discipline or location scope is an operator action; the assignment endpoint cannot change that scope.

## Current web API

| Method and route                            | Behavior                                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------------------- |
| `POST /api/auth/login`                      | Same-origin email/password form; verified Auth session in HTTP-only cookies        |
| `POST /api/auth/logout`                     | Same-origin sign-out                                                               |
| `GET /api/projects`                         | Authenticated user's projects under row-level security                             |
| `POST /api/projects`                        | Select an already authorized project; does not create a project                    |
| `POST /api/projects/:projectId/assignments` | Planner/manager command; version and scope checks; immutable assignment plus audit |
| `GET /api/health`                           | Web-process liveness only; does not claim database readiness                       |

Assignment JSON: `activityId`, `commandId` (UUID), `expectedVersion` (integer), `reporterId`, `supervisorId`, `from`, `to` (ISO dates), `reason`. Actor identity comes from the verified session; unknown fields are rejected. Reuse the same command ID and identical payload after a lost response. A different payload under the same ID or stale version returns 409; denied authority/scope returns 403; invalid fields return 422. See the planner's **Manage assignments** screen for a working client.

## Data and evidence boundaries

Plan revisions and assignment history are append-only. Same-project foreign keys prevent linking an activity to another project's member or WBS. Reporter activity access requires the latest assignment plus current membership, contractor, discipline and location scope. Historical/planned assignment dates control the Today/Up next grouping, not access expiration; earlier assigned activities remain visible for late reporting. Supervisor activity visibility is scoped; planner/manager access is project-wide. A reporter is never their own verifying supervisor.

The private evidence bucket currently supports a personal namespace: `projectId/userId/file`. The reporter can upload/read their own objects; an authorized project planner/manager can read them. Other reporters cannot. This is a tested Storage policy foundation, **not** a finished report-evidence API. Report-bound reservations, signed-download endpoints and stricter evidence routing arrive with reporting. A signed URL is a temporary bearer capability: already issued URLs remain usable until expiry even after membership revocation; newly requested URLs are denied immediately.

No direct actual-progress writes are granted to browser roles, including planners. Phase 3 writes through the guarded `decide_claim` transaction. Do not add direct client updates to `activity_actuals`. Live Primavera access, offline capture, speech and hosted production deployment remain outside the implemented slice.

## Phase 3 worker and text reporting

Apply all four migrations before starting the current app. On a disposable local database, `npm run db:reset:local` applies them in order, then `npm run local:bind` restores loopback-only published ports and `npm run seed:local` creates synthetic accounts. Reset erases existing local reports and decisions; do not use it merely to restart the app. Preserve the `intelligrid-local` Docker network setting described above.

Set `OPENAI_API_KEY` in the worker process environment or ignored `apps/worker/.env.local`. Never put it in `NEXT_PUBLIC_*`, web source, screenshots, or Git. The local launcher loads Supabase credentials from ignored `.cache/supabase.env`; the standalone worker instead requires `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`. See `apps/worker/.env.example`. Default model: `gpt-5.4-mini-2026-03-17`; change `OPENAI_MODEL` only after testing.

Run `npm run worker:start` alongside the web server. `npm run worker:start -- --once` handles at most one available job. The worker's `--check` path validates configuration boundaries without consuming jobs or calling the provider. The web process never receives the privileged worker credentials through application imports.

For a manual demo:

1. Sign in as a seeded field reporter. Choose **Type instead**, describe an assigned activity and a real work date, then **Check report** and **Send for review**. You may leave task selection blank to exercise matching.
2. Keep a second planner browser on **Schedule**. Its version must not advance while the report is merely submitted or extracted.
3. In a separate planner session, open **Review queue**, compare original wording with the candidate, enter a reason and accept an unambiguous event. FINISH needs a previously accepted START.
4. The schedule and overview refresh from accepted actuals. The reporter sees **Accepted**. The original baseline stays intact; external delivery remains pending.
5. Submit “Painting is finished.” without a location/date. Check the missing-detail flags and unchanged schedule. Follow-up questions are implemented in Phase 4, after this phase's review.

`npm run test:reconciliation-db` uses a disposable activity inside the synthetic isolation project, marks it inactive on completion, and retains test reports/audit history. Its injected provider is explicitly named `test-fixture`; it measures database rules, not model accuracy. Run database mutation suites sequentially and keep the worker stopped during these checks so it cannot take their controlled leases.

`npm run test:live` exercises real START and FINISH calls on CIV-0401; existing accepted dates are preserved on reruns. `npm run test:browser:live` uses the real provider and browser, accepts a start on an untouched civil activity and submits an ambiguous report. These commands consume API tokens and alter synthetic history. The browser test requires at least one untouched civil activity; use a deliberately reset disposable database when repeating it extensively. Live-test provider keys currently come from the process environment.

The versioned report/schedule/decision routes, bounded-read limits and failure behavior are documented in [Phase 3 technical notes](phase-03-technical-notes.md). Start the worker normally after controlled tests if you want newly submitted reports to process during the demo.
